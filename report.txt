MAIN REPORT
1. Executive Snapshot
Overall conclusion:n8n Backup Manager is not ready to serve as the sole backup and recovery mechanism for live, client-
facing, or business-critical SQLite-backed n8n deployments.
The application has a working foundation and several happy-path functions performed as expected. However, the core trust
guarantee - that a successful backup is recoverable and that a successful restore produces accessible data - was not proven
reliable in the tested SQLite scenarios.
The most serious issues are not cosmetic or minor. The application can produce misleading success states for backup and
restore. A user could believe they have a valid backup or completed restore, while the actual recoverable workflow data is
missing, stale, or hidden by WAL/SHM state.
Executive AreaAssessment
Overall QA RatingD - High Risk
Production ReadinessNot Ready for Business-Critical SQLite Use
Core Risk ThemeSuccessful responses do not consistently prove recoverable backup or visible restored data.
Immediate Decision
Do not rely on this tool as the sole DR mechanism until P0/P1 fixes are completed and
independently retested.
Retest Requirement
Clean-target backup/restore validation with artifact inspection and post-restore content
verification.
What works well
• The application starts in Docker and can be configured in a disposable QA sandbox.
• Authentication, local settings persistence, metadata display, scheduled backup success, retention, protected backups, delete
behavior, compression, encryption artifact creation/decryption, and missing-container failure handling had passing results in selected
core functional tests.
• The atomic SQLite backup path can create a complete artifact when sqlite3 is present inside the source n8n container.
Why the verdict remains high risk
• The fallback backup path can create a successful-looking artifact that omits WAL-resident workflow data.
• The application does not validate sqlite3 availability before backup, even though that prerequisite changes whether backup behavior is
safe.
• Restore behavior does not safely manage target WAL/SHM state or process lifecycle, so a complete restored base database can still
fail to show expected workflows after startup.
• Integrity checks and misconfiguration handling do not yet prove recoverability.

EVALUATION FRAMING
3. Engagement Context and Scope
The evaluated use case is a Docker-based n8n environment using SQLite, with potential personal, client-facing, and business-
critical workflows. The central question was simple: can the client trust that a successful backup means data is safe, and that a
successful restore means workflows are actually back?
In scope
• Repository baseline review and application purpose analysis.
• Docker sandbox capability and isolated setup validation.
• Local backup behavior and SQLite artifact inspection.
• Same-target and clean-target restore behavior.
• sqlite3-enabled atomic backup path.
• SQLite WAL/SHM restore lifecycle behavior.
• Selected core application features including scheduling, retention, compression, encryption, integrity checks, metadata, and error
handling.
• Findings, risk classification, readiness scoring, and remediation roadmap.
Out of scope for this phase
• Full penetration test or security audit.
• Production deployment hardening.
• Source code remediation or implementation work.
• Full retesting of Google Drive, S3, OneDrive, Telegram, or long-term cloud storage integrations.
• Long-term performance, stability, or uptime monitoring.
• Legal, regulatory, or compliance certification.
Cloud storage was intentionally deferred. Uploading an incomplete or unrecoverable local backup artifact to the cloud does not
create meaningful recovery protection. Local artifact correctness and restore correctness must be proven first.

HOW THE CONCLUSION WAS REACHED
4. Testing Methodology
• Established a repository baseline and identified architectural areas relevant to backup and restore trust.
• Confirmed that disposable Docker-based QA resources could be used safely and repeatably.
• Created isolated QA n8n and Backup Manager containers using local-only ports and dedicated sandbox folders.
• Created test workflow data and performed manual local backup smoke testing.
• Inspected SQLite artifacts directly using disposable helper containers.
• Compared live SQLite state against extracted backup databases.
• Performed same-target restore, clean-target restore, sqlite3-enabled atomic backup testing, and WAL/SHM restore lifecycle analysis.
• Ran a selected core functional test suite covering additional local features and failure behavior.
• Converted raw QA results into a findings register, risk classification, readiness score, and remediation roadmap.

ACTION PLAN
8. Remediation Roadmap
Fix Now - P0 / Critical
• Remove or block unsafe direct-copy fallback for live SQLite WAL databases.
• Fail backup loudly when atomic SQLite backup cannot run.
• Safely manage SQLite WAL/SHM files and target process lifecycle during restore.
• Validate SQLite db_path and reject backups that target an empty or non-n8n database.
• Add clean-target restore validation as a required release test.
Fix Next - P1 / High
• Add sqlite3 prerequisite validation and surface readiness in the UI/API.
• Upgrade integrity checks so they prove recoverability, not just readability.
• Improve error messages around encrypted backups, missing keys, and scheduled failures.
• Document supported SQLite backup modes and prerequisites clearly.
Improve Later - Operational Maturity
• Add automated test coverage for happy path, failure path, and restore verification.
• Add structured logs and recovery-oriented events.
• Add cloud-storage retesting after local artifact correctness is proven.
• Add release readiness gates for backup artifact inspection and clean-target restore validation.

11. Source Documents and Retention Notes
The source materials should be retained with the engagement record. If the application owner remediates the issues, the original
report and evidence index should be used to design the retest package.
Recommended retest package
• Preflight validation of sqlite3 availability and supported SQLite backup mode.
• Backup creation test where sqlite3 is absent - expected result should be a loud failure, not a successful fallback.
• Backup creation test where sqlite3 is present - expected result should be a complete artifact with expected workflow data.
• Clean-target restore test from a complete artifact - expected result should show the restored workflow after target startup.
• WAL/SHM handling test - expected result should prove old target WAL/SHM does not override restored base database.
• Invalid db_path test - expected result should be failure with clear message, not a successful backup record.
• Integrity check test - expected result should prove restore-readiness rather than just archive/database readability.
Final client decision
Do not approven8n Backup Manager as the sole backup and recovery mechanism for business-critical SQLite-backed n8n
environments until the P0 findings are remediated and independently retested. The application has a promising foundation, but its
recovery trust guarantee is not yet reliable enough for critical use.
